# Research-to-executable-evidence mapping — agent systems, Sep–Oct 2026

Status: source-linked research and validation design. No benchmark result below is proof of an installed LBE/Brew capability.

## Evidence classification rules
Store `source_uri`, original publication date, sample size, evaluated configuration, observed outcome, limitation, target subsystem and specific falsifier. Separate verified source claims, predictions, design proposals and local implementation observations. Prefer direct paper/source evidence to headline percentage. Reject reports that assert a complete fix from benchmark success.

## Research families and testable transfer
- **Trust layer / evidence withdrawal (Oct 1–9):** match final claims to trajectories, tools, artifacts, and repeated runs; deliberately withdraw or reverse decisive evidence. Acceptance: confidence does not persist after support disappears.
- **Compaction safety and tool governance (Sep 11–25):** self-written summaries cannot introduce authority; untrusted MCP/tool/skill metadata cannot silently grant permission. Test egress paths and malicious names, descriptions and returns.
- **SpecHarness / HEXIS (Sep 18–25):** distinguish agent proposals from runtime-committed proof and compile deterministic order constraints into guard states. Trace every obligation to a source and invalidate proof on artifact drift.
- **DelegateGuard / TreeFlex (Oct 9–16):** delegated grants attenuate and branch checkpoints are immutable; verify descendant revocation and original-trace recovery.
- **Bemula / experience curation (Oct 9–16):** deletion must cover dependencies; learned memory value requires a no-memory comparison and held-out improvement.
- **MCP-GRANITE and CoBRA (Aug–Sep):** choose tool interfaces by observed marginal task benefit; benchmark task-sized schemas and model choice separately from privilege.
- **Production simulation / ProgramDistill (Sep):** score cumulative replay of user journeys, with visual checks and true installed-effect acceptance kept separate.

## Method
For each claimed improvement add a failing baseline fixture, implement only in the owning subsystem, and retest with changed evidence/tool labels/context, repeated execution and a protected effect receipt. Store negative and inconclusive results as such. Cite paper limitations and dates. Watch ML serving updates only where matching real deployment hardware exists.

This document consolidates the user-provided weekly brief material, rather than validating each paper independently. External papers and source URLs should be independently retrieved before any causal-performance claim is promoted.
